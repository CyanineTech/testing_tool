# HTTP / gRPC 调用链超时

## 适用范围
- RCS 主机与从机之间、主机内部服务之间的 HTTP / gRPC 调用超时、失败或长时间卡住。
- 适用于“接口在线但调用慢”“主机调从机失败”“链路某一段超时”。

## 历史复盘优先

- 这类问题如果已经恢复，优先固定故障时间、重启时间或请求失败时间，再回看对应历史日志。
- 不要直接拿当前端口、当前容器或当前进程状态替代历史主机故障证据。
- 当前状态只适合作为补充，历史时间窗口内的调用链、服务链和依赖链证据更关键。

## 典型现象
- 某个接口偶发超时，但服务进程本身还在。
- 任务链路中前一段正常，后一段长时间没有回执。
- 主机或从机日志报 gRPC 超时、HTTP 连接失败、重试过多。
- 问题集中在某一类服务调用，而不是全局服务挂掉。

## 优先检查
1. 先确认是单次偶发超时还是持续性链路超时。
2. 检查请求发起侧和接收侧日志，确认到底卡在哪一段。
3. 对照 `python-ros-call-chain-monitoring.md` 中的调用链落点，查看 HTTP / gRPC 两端是否都在线。
4. 再区分是网络、依赖服务、线程阻塞还是调用目标未响应。

## 关键日志
- 主机后端日志
- 从机后端日志
- `task_running_server`、`map_server`、`backend_fastapi` 相关日志
- HTTP 接口访问日志
- gRPC 服务日志

## 常见检索词
- grpc 超时
- http 超时
- 调用链超时
- 请求卡住
- patch 接口失败
- 服务间调用失败

## 判定口径
- 如果服务本身活着但调用经常超时，更像链路、依赖或线程阻塞问题。
- 如果调用目标根本不在线，更像服务状态或端口可用性问题。

## 常见根因
- 调用目标响应慢或线程阻塞。
- 网络、路由或主从机链路抖动。
- 上游依赖异常，导致下游调用堆积。
- 重试策略过多，放大了链路时延。

## 处理建议
1. 先定位具体卡在哪一跳，不要笼统归因到“后端慢”。
2. 如果是持续超时，优先恢复被调用端或依赖端健康状态。
3. 如果是偶发超时，结合时间点查资源占用、依赖波动和网络抖动。
4. 修复后复测同类调用链，确认不是只恢复单个接口。
