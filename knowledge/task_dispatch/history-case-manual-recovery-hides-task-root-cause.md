# 历史案例：人工干预后任务恢复，但根因被掩盖

## 适用范围

- 任务最初卡住、失败或长时间不推进，现场通过手动切模式、重发任务、人工释放机器人后又恢复。
- 适用于“最后看起来恢复了，但想追最初为什么卡住”的历史复盘。

## 典型现象

- 任务一开始卡住，人工点继续、重发、切手自动或释放机器人后恢复。
- 最终任务完成，但中间某一跳的异常被人工操作覆盖。
- 主机页面最后状态正常，容易误判成“没问题，只是偶发”。

## 历史复盘优先

- 这类问题必须优先查第一次卡住的时间点，而不是人工恢复后的最终状态。
- 先固定首次异常时间、人工干预时间、任务恢复时间，再按时间线回看任务状态和回执。
- 不要因为最后任务完成，就跳过最初的断点分析。

## 优先检查

1. 先确认首次卡住的时间点和现场做过哪些人工操作。
2. 再区分是派发链路卡住、状态机卡住、事件条件不满足，还是回执没回流。
3. 对照主机任务日志、从机动作日志和人工操作时间，判断是哪一步先异常。
4. 如果人工操作包含切模式、重启节点或重发任务，要把这些动作从根因证据里剥离出来。

## 关键日志

- 主机任务状态流日志
- `task_running_server` 日志
- 从机 `default.launch`
- 从机 `mobile_base.launch`
- 现场人工操作记录或飞书对话时间点

## 常见检索词

- 手动恢复后好了
- 点继续后恢复
- 人工释放后恢复
- 切手自动后恢复
- 重发任务后好了
- 最后正常但想查根因

## 判定口径

- 如果首次异常时间与人工恢复时间之间存在明显空窗，更像中间某一跳真实卡住。
- 如果人工操作一做就恢复，但之后同类任务还复现，根因通常仍在原链路中。

## 常见根因

- 任务状态机在某一步等待条件时卡住。
- 事件回执没回流，人工操作绕过了原状态。
- 从机局部动作已执行，但主机未收到关键完成信号。
- 人工重发任务覆盖了第一次失败现场。

## 处理建议

1. 先围绕第一次异常时间复盘，不要围绕“恢复后的最后状态”分析。
2. 先把人工操作时间线单独列出来，避免污染根因判断。
3. 如果同类任务经常靠人工恢复，优先沉淀成状态机或回执链路专项。
